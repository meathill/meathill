# 报告与问题记录格式

## 建议输出结构

### 1. 测试目标与范围

- 测试角色：运营人员、客户、委托方、内容编辑
- 测试站点：前台 URL、CMS URL
- 测试边界：是否包含后台、是否包含多语言、是否包含移动端、是否允许创建数据

### 2. 测试用例

- 用业务语言描述用例，不要写成自动化断言
- 每条用例最好包含：场景、目标、入口、预期业务结果
- 可按首页、内容发现、转化、CMS、预览、多语言、移动端分组

### 3. 执行结果

- 每条用例都标记为 `通过`、`部分通过`、`失败`
- `部分通过` 必须说明哪些部分可用、哪些部分不可用
- 优先写出运营或客户真正看到的结果，再补充技术证据
- 使用简洁台账记录：用例、状态、URL、账号/角色、证据编号、测试数据标记、清理状态
- 保存、删除和状态变更只有在刷新、重新进入或新会话后仍符合预期，才可以标记为通过

### 4. 证据索引

- 把截图保存为可交付文件，不要只依赖浏览器会话中的临时画面
- 推荐命名：`序号-页面-视口-问题关键词.png`，例如 `03-order-mobile-sidebar-blocked.png`
- 每份证据注明页面 URL、账号/角色、viewport、测试数据标记和对应问题
- 必要时保留操作前后两份证据，帮助确认状态变化和清理结果
- 控制台、网络请求和代码路径只能作为辅助证据，不能代替用户可见现象

### 5. 问题记录

每个问题至少包含以下信息：

- 标题：一句话说清用户可见问题
- 严重性：高 / 中 / 低
- 页面或模块：URL、CMS 集合或具体功能入口
- 重现步骤：尽量短、可重复
- 复现状态：稳定复现 / 偶发 / 单次观察，待确认
- 实际结果：用户或运营看到什么
- 预期结果：本应如何工作
- 业务影响：为什么这会影响对外服务、留资、发布或维护效率
- 完成标准：修复后可以怎样从用户界面验证
- 证据：引用证据编号；必要时补充控制台、网络请求或代码路径
- 原因判断：将确认原因和推测原因分开；没有独立证据时不要把时间相关写成因果

### 6. 测试数据与清理

- 列出本轮创建或修改的数据标记、记录 ID、所在页面和最终状态
- 明确哪些数据已经清理并复查，哪些未能清理以及原因
- 单独列出邮件、通知、支付、发布或 webhook 等无法撤销的外部副作用

### 7. 验收结论

- `通过`：关键任务均可完成，且没有影响身份边界、数据持久化、数据正确性或核心流程的高严重问题
- `有条件通过`：主流程可用，但存在已明确接受风险、绕行方案和关闭条件的问题
- `不通过`：存在身份绕过、数据丢失、关键指标错误、核心业务流程无法完成或其他高严重阻断
- 写清判断依据、尚未覆盖的范围和仍需确认的开放问题，不要只给结论标签

## GitHub Issue 书写原则

- 验收报告可以按共性聚类；创建 issue 时，把聚类拆成可独立修复和验收的用户问题
- 一条 issue 只写一个问题，不要把多个独立症状堆在一起；一个报告发现可以映射成多个 issue
- 创建前搜索 open 和 closed issue，避免重复；优先复用仓库已有 label，不假设一定存在 severity label
- 标题写用户可见问题，不要只写底层原因
- 正文优先写：环境、步骤、复现状态、实际结果、预期结果、业务影响、完成标准、证据
- 只有在确认有帮助时再补充代码线索、日志或可疑根因
- 如果是脏数据问题，也要写清楚为什么系统允许它流入线上

## 严重性判断

- 高：直接阻断留资、购买、发布、预览，或让对外页面明显失效
- 中：明显损伤可用性、可信度或运营效率，但存在绕行方案
- 低：不阻断主流程的细节问题、资源缺失或控制台噪音

## 交付时别遗漏

- 明确哪些测试数据已清理，哪些未清理
- 明确哪些问题已建 issue，哪些还只是本轮记录
- 明确哪些结论来自浏览器观察，哪些来自代码或网络日志辅助确认
- 提供证据索引和报告发现到 issue 的映射，确保问题可以追踪到原始观察
