# Website Operator QA

当目标是判断一个网站能不能真正支撑内容运营和对外服务，而不是验证实现层面的 e2e 断言是否通过时，使用这个 skill。

## Core Stance

- 把自己当成普通运营人员、客户、委托方或内容编辑，不是开发者。
- 先看业务结果，再看实现细节。优先判断能否展示内容、承接线索、维护资料、预览发布、处理消息。
- 优先用真实浏览器交互完成测试。代码、网络日志和仓库文档只用于补充上下文或解释已确认的问题。
- 不要把这项工作做成自动化 e2e，除非用户明确改了目标。

## Test Integrity

- 把成功提示视为待验证信号，不视为完成证据。对创建、编辑、删除和状态变更，通过刷新、重新进入或新会话确认结果已持久化。
- 执行写操作前，确认影响范围、测试数据标记和清理路径；记录必要的前置状态，避免误改正式数据。
- 使用唯一且可搜索的测试标记。不要提交无法识别或无法清理的空记录，也不要为观察反馈而随意触发外部邮件、支付、发布等副作用。
- 只报告可观察到的现象。将推测原因单独标注；不要把一次时间相关当成因果。关键问题至少复现一次，无法稳定复现时标记为“单次观察，待确认”。
- 区分页面可用、任务可完成和业务可信。页面没有报错，不代表数据已保存、流程已闭环或指标正确。

## Workflow

1. Build scope
   - 确认前台 URL、CMS/admin URL、支持语言、是否已有登录态、是否允许创建测试数据。
   - 明确主要角色、关键业务任务、可接受的外部副作用和验收结论标准。
   - 若仓库可读，只读取必要文档：`README.md`、`TESTING.md`、`DEPLOYMENT.md`、`DEV_NOTE.md`、`WIP.md`，以及和内容模型或部署地址直接相关的文档。
   - 只有在登录凭据、不可逆操作或测试边界不明确时才提问。
2. Build a business-first test matrix
   - 从真实业务流程出发，不从路由或组件列表出发。
   - 覆盖前台浏览、转化路径、CMS 内容维护、预览、多语言、移动端、空状态和错误状态。
   - 对大型后台按工作流原型取样：至少覆盖查找记录、创建、编辑、状态推进、汇总核对和异常恢复；关键状态流转不得只靠页面抽样代替。
   - 需要详细清单时，读取 [references/test-matrix.md](references/test-matrix.md)。不要机械地把所有条目都跑一遍，要按站点类型取舍。
3. Execute manually in the browser
   - 用浏览器工具点击、输入、提交、切换语言、调整 viewport、查看可见反馈。
   - 维护简洁的执行台账。每个用例标记为 `通过`、`部分通过` 或 `失败`，并同步记录 URL、账号/角色、证据编号、测试数据标记和清理状态。
   - 如果同时有前台和 CMS，就把两条链路都测到：
     - 前台：客户能否找到内容、理解价值、完成转化。
     - CMS：运营能否找到入口、编辑内容、保存、预览，并信任最终结果。
   - 创建尽量少的测试数据，优先用草稿或明显可识别的临时名称，例如 `test-operator-qa-YYYYMMDD`。
   - 对保存、删除和状态变更验证重新加载后的结果；对汇总指标回到明细核算口径；对跨页面实体核对名称、编号和状态是否一致。
4. Record issues with business impact
   - **必填证据**：route URL、使用的测试账号/角色、关键截图；保存截图并建立证据索引，不能只依赖会话中的临时画面。
   - 记录重现步骤、实际结果、预期结果和业务影响。
   - 分开记录用户可见现象、复现状态和推测原因。只有稳定复现或有独立证据支持时，才把因果写成确认结论。
   - 优先上报会阻断线索收集、内容发布、导航浏览、客户信任或运营效率的问题。
   - 系统 bug 和内容/数据质量问题都要记录，但要明确区分。
   - 如果是通过代码或网络日志才确认的原因，把这些作为辅助证据，不要替代用户可见的问题描述。
5. Clean up after testing
   - 删除本轮创建的临时文章、产品、媒体、询盘或其他记录，除非用户明确要求保留。
   - 删除后通过搜索、刷新或重新进入确认数据已消失；外部消息或其他不可撤销副作用要单独记录。
   - 报告里注明哪些测试数据未能清理干净。
6. Deliver a usable report
   - 需要输出结构时，读取 [references/reporting.md](references/reporting.md)。
   - 默认交付包含：测试范围、测试用例、执行结果、证据索引、问题列表、开放问题或假设、测试数据清理结果，以及按需创建的 GitHub issues。
   - 给出 `通过`、`有条件通过` 或 `不通过` 的总体结论，并写明判断依据。存在身份绕过、数据丢失、关键数据错误或核心业务流程无法完成时，不得判定为通过。

## What To Look For

- 转化链路：询价、联系、预约演示、订阅、样品申请、报价请求
- 内容完整性：缺标题、空白区块、错误占位图、未翻译内容、日期或 slug 异常
- CMS 可维护性：列表可读性、筛选、空状态、表单校验、保存反馈、预览准确性、媒体复用、状态流转
- 访问边界：未登录直达、失败登录后的访问、退出后的会话状态、不同角色可见范围；只做普通用户可观察的边界验证，不扩展为渗透测试
- 数据可信度：刷新后是否保留、Dashboard 汇总是否能由明细解释、同一实体跨页面是否一致、数据源声明是否符合实际表现
- 业务闭环：状态是否有可执行的推进动作、处理结果是否留痕、异常后是否有恢复路径，而不只是展示状态或提供通用 CRUD
- 信任信号：联系方式、法务页、规格参数、发布日期、导航是否重复或失控
- 异常表现：请求打到错误环境、静默 fallback、404 占位资源、无指导性的错误提示

## Severity Heuristic

- 高：阻断成交、留资、内容发布，或让真实客户明显觉得站点坏了
- 中：严重影响内容发现、运营效率或信息可信度，但存在绕路方案
- 低：细节打磨问题、控制台噪音、favicon 缺失、非阻断视觉问题

始终用业务语言解释严重性，不要只给技术标签。

## Guardrails

- 不要因为页面没报错就判定“可上线”。
- 不要把允许发布脏数据的问题归咎于运营填得不好。
- 不要为了测试去静默修改线上正式内容。
- 不要留下难以识别的测试数据。
- 如果用户要求建 GitHub issue，先搜索已有 open/closed issue；一条 issue 只对应一个用户可见问题，并写明可验证的完成标准。
- 如果后续转入修 bug，结束本 skill 的测试报告职责，再切回正常研发流程。
