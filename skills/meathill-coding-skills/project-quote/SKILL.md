# 项目报价技能

帮助用户系统化地评估项目开发量、拆解工作项、估算工时，最终生成一份专业的 Markdown 报价文档。

全程使用中文交互和输出。

---

## AI 辅助开发效率与服务档位

本技能的工时估算默认基于 AI 辅助开发的实际效率，而非传统人工开发经验值。

- **AI 高度压缩工作**：编码、自动化测试代码、基础设施代码，工时 = 传统经验值 × **0.1**。
- **部分压缩工作**：架构、UI/UX、人工测试、安全审查、文档，按服务档位核算，不再套用 0.1。
- **人工约束工作**：沟通、验收、翻译审核、数据标注、运营，按实际需要核算。

技能清单中的基线已经按 ×0.1 换算，不得再次折算。复杂架构按实际组件和业务量计入，只有首次使用或明显不熟悉的技术才增加学习风险。

默认提供三档辅助工时，三档核心功能范围一致：

| 档位 | 辅助工时 | 适用情况 |
|---|---:|---|
| 核心开发 | 编码工时 ×20% | 预算紧张，复用现有设计与平台，保留必要质量、安全和交付基线 |
| 平衡交付 | 编码工时 ×45% | 完整需求梳理、主要流程体验优化、完整模块回归和使用文档 |
| 宽松高质量 | 编码工时 ×80% | 深化设计、兼容/性能/安全测试、完整运维验收材料和更多培训支持 |

安全、测试、备份、文档、部署和源码交付属于默认交付基线，其工时已经包含在编码与辅助工时中，不得再增加“安全费”“测试费”“文档费”等重复收费项。

## 默认交付基线（包含在整体报价中，不单独计价）

所有档位都必须在对客报价中明确列出以下基线。核心档可以减少广度和精细度，但不得取消可靠性、安全性、可维护性和可交接性的最低要求。

### 数据安全与可靠性

- 配置数据库和文件定期自动备份、最近 7 天保留、加密存储和恢复流程。
- 上线前至少完成一次恢复验证；交付 migration、版本记录和回滚方案。
- 敏感数据加密或脱敏，日志不记录密码、验证码、Token 等信息。
- 关键业务操作和数据修改留痕；云存储与备份的实际资源费用由客户承担。

### 代码及知识产权交付

- 代码进入客户持有或最终移交给客户的 GitHub 仓库，保留可理解的提交历史、版本标签和发布记录。
- 交付完整源码、数据库 migration、构建/部署配置、依赖与第三方服务清单、环境变量模板，不写入真实密钥。
- 客户拥有代码、云平台和第三方账号的最终控制权；不得依赖只存在于开发方个人设备上的脚本或配置。

### 代码质量

- 执行 TypeScript 类型检查、格式化、lint、构建检查和依赖完整性检查。
- 提供单元测试、集成测试及关键业务链路测试，并在 CI 中运行适用检查。
- 对认证、支付/核销、异步任务状态、权限、数据一致性等关键逻辑提供回归测试。
- 交付 README、部署说明、数据结构说明及必要的 API/任务协议文档。
- 保持模块化和可复用，避免明显重复逻辑和失控的单文件复杂度。

### 应用安全

- 使用交付时仍受官方支持、无已知高危漏洞的稳定版本，不机械追逐未经验证的最新版本。
- 使用 ORM 或参数化查询；合理使用事务、唯一约束、外键、幂等键和并发状态检查。
- 落实输入校验、输出转义、富文本白名单，以及 SQL 注入、XSS、CSRF、SSRF、路径遍历、危险文件上传和命令注入防护。
- 落实登录失败限制、Session/Token 有效期、RBAC、最小权限、API 鉴权、限流、CORS、安全响应头和错误脱敏。
- 上传文件同时校验扩展名、MIME 和文件头，并与 Web 根目录隔离；交付前执行依赖安全扫描。

### 部署与运维基础

- 开发、测试和生产环境分离；密钥通过平台 Secret 管理，不提交到 Git。
- 提供自动化或可重复执行的部署、日志、健康检查、基础异常监控和关键任务告警。
- 异步任务具备幂等、重试、超时、失败状态和孤儿任务恢复；交付版本标签、回滚步骤和故障恢复说明。
- 提供分页、批处理、并发限制、合理缓存和避免明显 N+1 查询等基本性能保障。
- 完成基础响应式适配和主流浏览器检查。

## 首次初始化：创建技能清单

当技能清单不存在时，系统性地询问用户的技术储备。**分批提问，每次一个类别：**

**第一批：前端**
- 你常用的前端框架有哪些？（React/Vue/Angular/Svelte/其他）
- 常用的 UI 组件库？（Ant Design/Element Plus/shadcn/Tailwind CSS/其他）
- 是否做移动端/小程序开发？用什么框架？

**第二批：后端**
- 常用的后端语言和框架？（Node.js + Express/Koa/Hono/NestJS、Python + Django/FastAPI、Go、Java、PHP、其他）
- 常用的 ORM/数据库工具？（Prisma/Drizzle/TypeORM/Sequelize/其他）

**第三批：数据库与缓存**
- 常用哪些数据库？（PostgreSQL/MySQL/TiDB/MongoDB/SQLite/其他）
- 是否使用缓存？（Redis/Memcached/其他）
- 是否使用搜索引擎？（Elasticsearch/Meilisearch/Algolia/其他）

**第四批：部署与基础设施**
- 常用的部署方式和平台？（Cloudflare Workers/Vercel/Netlify/Docker + 自建服务器/阿里云/腾讯云/AWS/GCP/其他）
- CI/CD 用什么？（GitHub Actions/GitLab CI/其他）
- 是否使用消息队列？（RabbitMQ/Kafka/其他）

**第五批：第三方服务**
- 常对接哪些第三方服务？（微信支付/支付宝/短信/邮件/微信公众号/OAuth/地图/其他）

收集完毕后：
1. 为用户提到的每种技术，生成一份操作类型 + 三档工时（简单/中等/复杂）的表格
2. 表格格式参考下面的模板
3. 展示给用户确认和调整
4. 确认后写入 `references/skill-inventory.md`

**技能清单中每种技术的格式：**

```markdown
### 技术名称
| 操作类型 | 简单 | 中等 | 复杂 | 说明 |
|---|---|---|---|---|
| 操作A | Xh | Yh | Zh | 备注 |
| 操作B | Xh | Yh | Zh | 备注 |
```

按类别分区：前端框架、后端框架、数据库、缓存、部署平台、CI/CD、第三方服务集成。

末尾附上调整因子：
- 首次使用某技术：+30-50%
- 紧急交付：+20-30%
- 需求不明确：+20-40%
- 多语言支持：+15-25%

## 模式 B：项目报价（主流程）

### 阶段一：需求收集

**如果用户提供了以前的报价文档作为参考：**
- 先读取并分析该文档
- 提取格式风格、章节结构作为本次报价的参考模板
- 提取历史工时估算作为参照基准
- 后续报价中尽量保持风格一致

**如果用户提供了需求文档/PRD：**
- 先完整读取
- 提取关键信息后，只问补充性问题

**如果都没有，分批向用户提问（每次 3-4 个）：**

第一批：
- 项目名称是什么？客户名称？
- 这是什么类型的项目？（Web 应用/移动 App/小程序/API 服务/管理后台/其他）
- 简单描述一下项目的核心功能

第二批：
- 目标平台有哪些？（Web/iOS/Android/微信小程序/多端）
- UI/UX 设计是否包含在你的报价范围内，还是客户提供设计稿？
- 有没有需要对接的已有系统或第三方服务？

第三批：
- 有没有特殊的性能/可扩展性要求？
- 客户的期望交付时间是什么？
- 你的时薪费率是多少？（如果不想在文档中体现费率，可以跳过）

### 阶段二：项目拆解 + 技术选型

1. 将项目按 **模块 → 功能项** 分解：
   ```
   项目
   ├── 模块1（如：用户系统）
   │   ├── 功能1.1（如：注册/登录）
   │   ├── 功能1.2（如：个人资料管理）
   │   └── 功能1.3（如：权限管理）
   ├── 模块2（如：内容管理）
   │   └── ...
   └── 基础设施
       ├── 部署配置
       ├── CI/CD
       └── 监控
   ```

2. 从已加载的技能清单中，选取本项目需要的技术栈，并先判断现有平台可复用范围。
3. 技术选型按“预算约束 + 技术熟练度 + 运行适配性”排序：
   - 预算越紧，越优先复用存量系统和用户熟悉的技术，避免无收益的平台迁移。
   - 熟悉的多 Worker、Queue、Web、数据库和对象存储组合不得因架构组件多而自动叠加学习风险。
   - 长时间 CPU/GPU、PDF 解析或本地模型任务必须进入适合的容器/计算 Worker，不要为追求统一而塞入不合适的请求生命周期。
4. 如存在有意义的技术路线差异，给出“主报价 + 可选路线调整”，说明价格、周期、客户资源费和运维差异，避免生成难以阅读的全排列报价矩阵。
5. 用表格展示模块拆解和技术选型，让用户确认后再进入估算。

### 阶段三：工时评估

基于技能清单中的 ×0.1 编码基线，结合项目实际复杂度进行估算。每项必须能追溯到需求或交付物，禁止先定总价再反向凑工时。

**输出明细表格：**

| 序号 | 模块 | 功能项 | 交付/验收结果 | 技术栈 | 复杂度 | 编码工时(h) | 备注 |
|------|------|--------|---------------|--------|--------|--------------|------|
| 1 | 用户系统 | 注册/登录 | 可注册、登录、退出并通过权限测试 | React + Node.js | 中 | 6 | 含 OAuth |
| ... | | | | | | | |

先计算编码小计，再同时生成三档辅助工时与总价：

| 档位 | 编码工时 | 辅助比例 | 辅助工时 | 总工时 | 内部核算金额 | 对客固定报价 |
|------|---------:|---------:|---------:|-------:|-------------:|-------------:|
| 核心开发 | XXX | 20% | XXX | XXX | XXX | XXX |
| 平衡交付 | XXX | 45% | XXX | XXX | XXX | XXX |
| 宽松高质量 | XXX | 80% | XXX | XXX | XXX | XXX |

默认基于同一核心功能范围报价。差异只能来自需求梳理、设计精度、测试广度、文档、培训、沟通频率和维护容量；必要的数据安全、代码质量、应用安全和可交付性不得降档取消。

内部核算稿必须显示公式、费率、取整和风险假设；对客版不得出现 AI 折算、内部费率、风险推理或修订过程。展示给用户确认后再生成正式文档。

### 阶段四：技术方案

编写简要的技术方案说明，包括：
- 前端、API、异步任务、计算 Worker、数据库、文件存储和部署选型及理由
- 现有系统复用边界，以及为什么该方案符合预算和用户技术习惯
- 异步任务的队列、状态、重试、幂等、监控和故障恢复
- 关键第三方服务、客户直接承担的资源费
- 可选技术路线的价格与周期调整

内容不需要太深入，目的是让客户了解技术选型的合理性。

## 模式 C：竞品 / 参考站点分析

当用户提供一个竞品或参考站点的 URL，希望以此为基础生成报价时，执行以下流程。

### 步骤一：系统性遍历站点

按以下顺序访问页面，**每个页面访问后立即记录其实际 URL**，以及发现的功能点：

1. **首页** — 核心价值主张、产品分类入口、导航结构
2. **产品列表页** — 筛选/排序方式、产品卡片信息、分页/无限滚动
3. **产品详情页** — 规格配置选项、实时报价/计算、图稿上传、加入购物车
4. **注册/登录页** — 注册字段、OAuth 方式、B2B 审核流程（如有）
5. **用户中心 / 账户页** — 个人资料、地址管理、订单历史
6. **下单/结账流程** — 配送选项、支付方式、优惠码
7. **订单追踪页** — 状态流转、物流信息
8. **帮助中心 / FAQ** — 内容结构、分类方式
9. **其他内容页** — 关于我们、联系方式、博客/案例（如有）
10. **后台/管理入口**（如能访问）— 管理功能概览

遍历过程中，如果发现新的重要页面类型（如定价页、API 文档、合作伙伴页等），也一并访问并记录 URL。

### 步骤三：建议分期规划，请用户确认

根据功能重要性和依赖关系，建议一期 / 二期拆分：

- **一期（MVP）**：核心业务链路必须的功能，上线即可运营
- **二期（增强）**：锦上添花、可延后的功能

以表格形式展示，让用户确认或调整：

| 功能点 | 建议分期 | 说明 |
|--------|----------|------|
| 用户注册/登录 | 一期 | 核心流程 |
| 实时报价计算 | 一期 | 核心差异化功能 |
| Dropshipping | 二期 | 增值服务，可延后 |
| ... | | |

用户确认一期范围后，直接进入**模式 B 的阶段二**（项目拆解 + 技术选型），以确认的功能列表作为需求输入。

## 注意事项

- **不要一次性问太多问题**，每次最多 3-4 个，保持对话节奏
- **工时估算要务实**，参考技能清单中的基线，避免虚高或虚低
- **表格数据要一致**，明细加总必须等于汇总数字
- **避免重复收费**，默认交付基线只能包含在总价一次，不得又以安全、测试、备份或文档名义另行计费
- **对客清稿**，客户版不得出现 AI 折算、内部费率、内部风险推理、修订过程或口语化讨论
- **结果目标有边界**，OCR 准确率、搜索排名、AI 引用率等必须有基线和测量方式，不作无条件保证
- **如果用户提供了参考文档**，优先参考其格式和风格
- **报价编号**按 Q-年份-序号 格式自动生成（如 Q-2026-001）
- **始终用中文**，包括表头、类别名称、备注等
