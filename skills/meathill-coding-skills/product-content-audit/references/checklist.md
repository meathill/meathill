# Detailed Checklist

第一阶段审查时不必把每一条都跑一遍，按站点类型和最近改动有所取舍。这份清单存在的意义是：

- **避免遗漏**——你心里有了完整地图，再决定取舍才有意义。
- **给报告分门别类**——条目分类对应报告里的 finding 前缀（J/S/L/M/R/I）。
- **遇到拿不准的情况能查**——具体到"这种情况算高还是中"。

不要把它当成 SOP 死板地执行。

---

## J — Jargon & plain language

> 找出技术黑话，决定保留还是改写。详细规则见 [plain-language.md](plain-language.md)。

- [ ] 首屏 hero / slogan 是否包含开发者才能理解的词
- [ ] 主要 CTA 按钮 label 是否人话（"Get started" 通常 OK；"Initialize workspace" 通常不行）
- [ ] 价格页 / 套餐对比表里是否使用普通用户能换算成"我得到什么"的语言（避免 "5 dispatch tokens" 这种）
- [ ] 错误提示是否包含错误码、堆栈片段、英文异常名（普通用户视角下基本都不该有）
- [ ] 帮助 / 文档入口的标题是否能让人猜到点进去会看到什么
- [ ] 通知 / 邮件主题行是否人话（"Your job has completed" vs "Build #123 succeeded"）
- [ ] 中英混用文案里，英文部分是否是必须保留的品牌词，还是无意之间漏出的代码词

## S — Copy out of sync with code

> 拿最近 commit 当锚点，找页面文案没跟上的地方。

- [ ] 最近重命名的功能 / 套餐名 / 计划名是否在所有提到它的页面同步更新
- [ ] 最近下线的功能在 FAQ / 帮助 / 落地页 / 邮件模板里是否还有提及
- [ ] 最近新增的能力在落地页 / dashboard / onboarding 里是否被介绍
- [ ] 价格 / 限额 / 数字（"最多 X 个"、"每月 Y 次"）改了之后，是否还有页面在显示老数字
- [ ] 登录方式（Google / GitHub / 邮箱魔法链接 / 第三方）变化后，登录页与首页 CTA 是否一致
- [ ] README / 落地页 / app store 描述这三处的"产品一句话定位"是否一致
- [ ] 截图 / GIF 演示是否还反映当前真实 UI（不一致时记到中危）
- [ ] 改名了但 i18n key 仍是老名字 → 不改 key，只确认所有 locale 文本同步更新

## L — Missing links / CTAs / next steps

> 用户在每个页面的"下一步"是否清晰。

- [ ] 落地页：注册 / 试用 / 下载入口是否在首屏可见
- [ ] 落地页：是否提供"产品演示" / "查看示例"等次级 CTA
- [ ] dashboard：是否有"下载客户端"、"升级套餐"、"查看文档"、"联系支持"入口
- [ ] dashboard：新用户首次进入时，是否有 onboarding / 引导 / 示例数据
- [ ] 空状态：是否有可点击的下一步（"创建第一个 X"），而不仅仅是图标
- [ ] 错误状态：是否有"重试"、"联系支持"、"返回首页"中的至少一个
- [ ] 404 页：是否有搜索、返回首页、近期访问页、联系入口
- [ ] 设置 / 个人页：注销账号 / 修改密码 / 切换语言 / 删除数据等高敏操作是否可达
- [ ] 设置：删除账号 / 删除数据等不可逆操作是否有合理的二次确认
- [ ] 邮件模板：邮件底部是否有"为什么收到这封信" + "退订" 入口
- [ ] 法律页（隐私 / 服务条款 / cookie 政策）是否在 footer 可达——这关乎合规
- [ ] 移动端导航：抽屉菜单 / 底部 tab 是否覆盖关键入口（不是只为了好看而砍）

## M — SEO / Meta / OG

> 这一类问题不会让现有用户看不懂，但会让**新用户找不到你**。

- [ ] 每个公开路由是否有独立 `<title>`，并且不是 `Untitled` 或文件名
- [ ] `<meta name="description">` 是否存在、是否面向用户而不是开发者
- [ ] description 中是否含有占位符（lorem、TODO、"add a description"）
- [ ] `og:title`、`og:description`、`og:image` 是否齐备
- [ ] og:image 是否仍指向产品旧版本截图、域名、logo
- [ ] `lang` 属性是否随 locale 切换正确设置
- [ ] sitemap.xml / robots.txt 是否存在，是否还引用了已下线的路径
- [ ] manifest.json：name / short_name / theme_color 是否还反映当前品牌
- [ ] 多语言 hreflang 是否完整，缺一个 locale 会让搜索引擎只展示其中一种
- [ ] 关键页面是否被 `noindex` 误标（开发期常见）

## R — Readability / Micro-copy

> 不是大错，但累积起来会让产品显得不专业。

- [ ] 单段是否有超过 5 行的"墙体文字"
- [ ] 是否有句号 / 标点缺失或全半角混排（中文文案里）
- [ ] 按钮 label 是否是动作 + 名词（"创建简历"），而不是单词性（"提交"、"确认"）
- [ ] 表单 placeholder 是否在用户开始输入时仍能看到提示（如果用 placeholder 当 label 会丢失上下文）
- [ ] 必填项标记是否清晰
- [ ] toast / 通知文案是否完整成句，还是字段名 + 状态码
- [ ] 加载文案是否给出预期（"正在生成简历……"，而不是"加载中"）
- [ ] 数字 / 时间 / 货币格式是否随 locale 调整（"$10" vs "￥10"，"05/06" vs "06/05"）
- [ ] 复数处理（"1 file" vs "2 files"）在每种 locale 是否正确
- [ ] 敏感操作前的提示文案是否平静而不是恐吓（"删除后不可恢复" 比 "⚠️ 这个操作非常危险" 更有用）
- [ ] 占位符 / Lorem / TODO / coming soon / placeholder 等词是否漏到生产文案

## I — i18n gaps

> 多语言项目专用。原则是**先标记，不擅自补**。

- [ ] 所有 locale 文件的顶层 key 集合是否一致
- [ ] 缺 key 的 locale，运行时会显示 key 名还是回退？两种都不算"用户能用"
- [ ] 数字 / 单位 / 日期格式是否使用平台 i18n 工具，而不是硬编码
- [ ] zh / en 同一 key 的语义是否还指向同一件事（重命名后不一致是常见事故）
- [ ] 多语言里某些"庆祝"、"幽默"、"亲昵"语气是否在另一种语言中合适
- [ ] 是否存在硬编码字符串绕过 i18n（搜索 React 组件里的中英文字面量）
- [ ] 邮件 / OG / meta 是否随 locale 切换
- [ ] 错误页 / 404 页是否在每种 locale 下都有正确文案
- [ ] 切换语言后，URL 是否合理保留（这影响 SEO，但也是"用户能否分享当前页给同事"的体验问题）

## How to triage when scope is large

如果项目很大（比如 5000+ 字符串），不要试图一次跑完整张清单。建议的策略：

1. **第一次跑**：只看 J（黑话）和 L（缺失入口）——因为这是最容易让用户当场流失的两类。
2. **第二次跑**：补 S（与代码同步）——结合最近 commit。
3. **第三次跑**：补 M（SEO）和 I（i18n）——结合 sitemap / locale 文件。
4. **第四次跑**：R（micro-copy）扫尾。

把跑过哪几类记到报告 `0. Scope` 里，下次跑前先看上次的范围。

## When to skip the audit and ask the user instead

下面这些情况，**不要**自己输出 finding，先停下来问：

- 项目没有 README，或者 README 是默认 framework 模板——你不知道目标用户是谁，所有"口语化"判断都是悬在空中。
- 仓库里有多个独立产品（monorepo），没有说明审查目标——可能是 marketing 站、dashboard、admin 三个站点
- 多语言文件结构非常规（用 YAML、PO、自定义 loader 等），不确定哪个是真正的 source of truth
- 仓库目前正在大规模重构，commit log 里出现过 `WIP`、`refactor` 等 sweeping 改动——文案审查最好等重构告一段落
