# Plain Language Guide

口语化改写不是"把英文换成中文"或"把长句变短句"，而是**让一个第一次访问、不懂技术的人能在 5 秒内知道这是在做什么、要不要继续**。

## 改写的总原则

1. **看不懂的词换掉，看得懂但拗口的词留着**。"用户"和"账号"对普通人没问题，"实例"和"端点"才是问题。
2. **把名词改成动作**。"启用 webhook" → "在出现新订单时通知我"；"Configure your endpoint" → "设置接收通知的地址"。
3. **把"你需要做什么"放前面，原因放后面**。开发者写的文档常常先解释概念，普通用户更需要先知道下一步是什么。
4. **缩写第一次出现要展开，并用一句话解释为什么用户该关心**，而不是只展开。
5. **保留品牌专有名词**。产品自己起的名字不要替换，即使你觉得有更通用的说法。

## 常见技术词怎么处理

下面这张表只是参考起点，**不要直接套用**。审查时要先看上下文，判断这个词面对的是谁、能不能保留。

| 出现的词 | 普通用户会怎么理解 | 改写方向 |
|---------|------------------|---------|
| dispatch | 不知道，可能猜成"派遣" | 发送 / 推送 / 发出 |
| endpoint | 不知道 | 接收地址 / 接口地址（看上下文） |
| token | 可能联想成"代币" | 访问凭证 / 密钥 / 登录信息 |
| webhook | 不知道 | "事件发生时自动通知你" |
| OAuth / SSO | 大致知道是登录相关 | "用 X 账号登录"（X 是具体平台） |
| API key | 略懂 | 看用户群——开发者面向的产品保留即可 |
| dashboard | 多数人能猜 | 控制台 / 工作台（保留也可） |
| instance | 不懂 | 看上下文：服务 / 副本 / 项目 |
| SSR / CSR / SPA | 完全不懂 | 不要出现在用户文案里 |
| build / deploy | 开发者懂 | "发布" / "上线"（面向小白时） |
| render | 不懂 | "生成" / "显示" |
| hydration | 不懂 | 不要出现在用户文案里 |
| payload | 不懂 | "数据" / "内容" |
| timeout | 多数人懂 | 看上下文，"超时"通常没问题 |
| latency | 多数人不懂 | "延迟" / "等待时间" |
| throttle / rate limit | 部分人懂 | "次数限制" / "每小时最多 N 次" |
| async / await / Promise | 完全开发者词 | 不应出现在用户文案里 |
| cache | 多数人略懂 | "已保存的副本" 或保留 |
| migration | 开发者词 | "数据迁移" / "升级" |
| schema | 不懂 | "数据结构" / "字段" |
| polling | 不懂 | "定时检查" |
| log / stdout | 部分人懂 | "运行记录" / "日志"，stdout 永远换掉 |
| 404 / 500 / 502 | 多数人不懂数字 | "页面不存在" / "服务暂时不可用" |
| CORS / CSRF | 完全不懂 | 不应出现在用户文案里 |

## 改不改？决策树

```
出现疑似技术词
    │
    ├─ 这个词是产品本身的名字？  → 不动
    │
    ├─ 用户群是开发者？           → 多半不动，偶尔加一句解释
    │   （看 README、看着陆页定位）
    │
    ├─ 这个词出现在用户必经路径上？
    │   （注册、首次使用、升级、错误页）
    │   ├─ 是 → 必须改，归为 [高] 或 [中]
    │   └─ 否（出现在高级设置里）→ 可改可不改，[低]
    │
    └─ 拿不准？                   → 进 Open questions，让用户决定
```

## 几个语言层面的注意事项

### 中文文案

- **慎用四字成语和书面语**——"全方位赋能"、"赋予用户"、"打造卓越体验"这种在 SaaS 着陆页里到处都是，但在 side project / 工具类产品里通常显得空、显得装，反而拉低信任。
- **少用"您"**——除非品牌主调是非常正式的 to B 产品，否则在工具类产品里一律用"你"更亲切。
- **避免"基于"、"通过"、"实现"句式堆叠**——"基于 AI 实现的简历生成"不如"AI 帮你写简历"。
- **半角全角混排**——这是产品质感问题，但本 skill 不修，记到 [低] 即可。

### 英文文案

- **避免动词原形堆"-ing" 形式**——"Streamlining your workflow with AI-powered insights" 这种营销腔过重，工具类产品改成 "AI helps you work faster" 更直白。
- **少用 "leverage / utilize / synergize / empower"**——它们的含义在普通用户那里几乎为零。
- **句子开头大小写在按钮 / 菜单里要一致**——这是细节问题，记到 [低]。
- **am/pm 还是 24h、英式还是美式拼写**——按 README 里产品定位决定，本 skill 不主动统一。

### 中英共存的项目

- 不要主动把一种语言"翻"成另一种。**每种语言面对的是不同的人群**，可能需要不同的语气甚至不同的卖点。
- 同一个 i18n key 在两种语言下语义偏差大时，**先放进 Open questions** 让用户裁定。
- 中文里习惯的某些表达（"恭喜你 🎉"）直接搬到英文里可能显得不专业；反之，英文里的玩笑也可能在中文环境里显得轻浮。这种判断不要替用户做。

## 改写示例

### 示例 1：首页 hero（中文）

- 现：基于先进的 AI 算法，为您打造专属于您的简历生成体验。
- 议：让 AI 帮你写一份更容易拿到面试的简历。
- 由：原文里"基于"、"算法"、"打造"、"专属于您的体验"是四组叠在一起的营销词，普通求职者读完不会知道这工具能解决他什么问题。改写后的版本直接说出"求职者想要什么"。

### 示例 2：错误页（英文）

- 现：500 — Internal Server Error. The request could not be completed due to an unexpected condition.
- 议：Something went wrong on our side. We've been notified and are looking into it. Try again in a few minutes, or [contact support](mailto:...).
- 由：500 这个数字对用户没意义；"unexpected condition" 让用户无所适从。改写版告诉用户三件事：不是你的问题、我们知道了、你可以怎么继续。

### 示例 3：dashboard 空状态

- 现：暂无数据
- 议：还没有简历。点[新建]开始你的第一份。
- 由：空状态是用户最容易卡住的地方。"暂无数据"是开发视角；用户视角是"那我现在做什么"。

## 不要改的情况

- 文案出现在管理后台 / 调试页面 / 内部工具上——不是用户视角问题。
- 文案明显在引用产品本身的功能名（即使该功能名是英文）——保留。
- 文案是法律/合规要求的措辞（隐私政策、cookie 提示等）——不动，建议用户找律师而不是 AI。
- 用户在 README 里明确写过"我们就是要保留 nerdy 的语气"——尊重用户的产品定位。
